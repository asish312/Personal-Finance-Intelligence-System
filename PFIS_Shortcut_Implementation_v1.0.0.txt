PFIS v1.0.0 — iOS SHORTCUT IMPLEMENTATION GUIDE
Production backend: PFIS_TransactionEngine_v1.0.0.gs

1. RESPONSIBILITY BOUNDARIES

The iOS Shortcut is the mobile capture and receipt interface.
Google Sheets is the canonical ledger and financial workspace.
Apps Script is the transaction API and deterministic processing engine.
Gemini Tasks is an optional daily workbook assistant for Purpose suggestions. It is not called by the Shortcut or Apps Script.

2. CURRENT END-TO-END FLOW

Bank SMS / Email / Share Sheet
  -> capture the complete original message
  -> run the transaction extraction prompt
  -> if result is IGNORE, stop
  -> validate the ten-field txnString
  -> POST JSON to Apps Script /exec
  -> read success, status, nextAction, transaction and displayText
  -> route:
       SHOW_RECEIPT      -> display the transaction receipt
       CLASSIFY_CATEGORY -> classify only the missing/invalid category, validate exact category
       REVIEW            -> show the genuine review/conflict reason; no automatic approval
       SHOW_ERROR        -> show error and requestId
  -> if a category was validly resolved, POST one update request
  -> show the final backend response.

Purpose is optional. Do not create ASK_PURPOSE, prompt the user because User Notes is blank, or block a receipt because Purpose is blank.

3. SHORTCUT INPUTS

For every source alert, retain:
- sourceType: SMS or EMAIL
- originalText: complete original notification body
- txnString: exactly ten pipe-separated fields from the extraction prompt
- sender: optional sender
- subject: optional email subject
- requestId: optional unique correlation ID
- batchId: optional source batch ID
- token: only when WEB_APP_SECRET is configured

Do not replace originalText with an AI summary. Original evidence is required for source hashing, reconciliation and audit. Never include full account/card numbers in extra prompt context.

4. TEN-FIELD txnString CONTRACT

datetime | signed_amount | bank | account_type | instrument | type | merchant_name | counterparty | ref_no | balance_after

1. datetime — actual transaction date/time. Use date-only when no time is in the source.
2. signed_amount — outflows negative, inflows positive; two decimal places.
3. bank — financial institution/provider.
4. account_type — savings/current/credit card/wallet/etc., or NA.
5. instrument — UPI/card/NEFT/IMPS/net banking/etc., or NA.
6. type — expense/income/card_payment/investment/transfer/refund/NA.
7. merchant_name — readable merchant or transaction description.
8. counterparty — explicit sender/recipient when available, or NA.
9. ref_no — actual UTR/RRN/payment reference, or NA.
10. balance_after — actual post-transaction account balance only, otherwise NA.

Do not invent a current time or use SMS receipt time as transaction time. Do not use credit limit, available balance, statement balance or minimum due as the transaction amount. Never shift missing values into neighbouring fields. Unknown optional fields should be NA.

5. APPS SCRIPT REQUEST

Use the Shortcuts action Get Contents of URL:
- URL: deployed Google Apps Script Web App URL ending in /exec
- Method: POST
- Request Body: JSON
- Content-Type: application/json

Illustrative request; all sample values are fake:

{
  "action": "ingest",
  "sourceType": "SMS",
  "txnString": "14/10/2026 09:15:00|-845.50|Demo Bank|Savings Account|UPI|expense|Harbor Coffee|Harbor Coffee|DEMO-UTR-1001|NA",
  "originalText": "DEMO BANK: INR 845.50 debited at Harbor Coffee on 14/10/2026 at 09:15. Ref DEMO-UTR-1001.",
  "sender": "DEMO BANK",
  "requestId": "SHORTCUT-DEMO-001"
}

For email use sourceType=EMAIL and pass sender and subject when available. If WEB_APP_SECRET is configured in Apps Script Script Properties, include the matching token field. Never commit the token or put it in a public prompt.

6. RESPONSE ROUTING

Read:
- success
- status
- nextAction
- displayText
- transactionId
- transaction
- transaction.category
- transaction.userNotes
- transaction.needsReview
- transaction.reviewReason
- transaction.validationFlag
- allowedCategories (only for category classification)
- requestId

Use nextAction as the primary router.

SHOW_RECEIPT
Display displayText or a compact receipt with date, merchant, amount, category, account label and Transaction ID. RECONCILED and IDEMPOTENT_REPLAY should not trigger a second edit.

REVIEW
Show reviewReason, validationFlag and requestId. Do not automatically approve, archive, delete or change financial facts.

SHOW_ERROR
Show message/error and requestId. Do not display a success receipt.

CLASSIFY_CATEGORY
The engine could not assign a valid active category. Run the category fallback prompt using merchant, amount, type, current category, optional user note, original source message and allowedCategories. Trim the result and require an exact match to allowedCategories. If no exact match exists, do not update. If it matches, POST one update request.

Example category update (synthetic):
{
  "action": "update",
  "transactionId": "DEMO-TX-001",
  "category": "Food & Dining",
  "actor": "user",
  "reason": "shortcut_category_fallback"
}

Do not include Purpose merely to force an update. Do not send a fabricated category or NO_RELIABLE_CATEGORY.

7. PURPOSE POLICY

The backend has requiresPurpose=false. Missing Purpose:
- is valid,
- is not a required enrichment item,
- does not block ingestion or receipt display,
- is measured separately under getdataquality.response.data.missingPurpose.

A trusted rule may generate Purpose during insertion/reconciliation when Auto Purpose=TRUE or the supported Purpose Trigger is satisfied. A salary rule can use LAST_WORKING_DAY_OF_MONTH and an employer-scoped calendar. Recurrence alone does not authorise purpose inference.

Gemini's daily Purpose workflow is separate from the Shortcut:
- Gemini reads recent blank-Purpose transactions and source evidence.
- Gemini writes only to Purpose Review Queue with Status=SUGGESTED.
- A person verifies Source Log and changes Status to APPROVED with reviewer identity/date.
- Apps Script PFIS_APPLY_APPROVED_PURPOSE_SUGGESTIONS applies only the approved suggestion, preserving audit history.
- The Shortcut does not ask Purpose.

See PFIS_Gemini_Purpose_Enrichment_v1.0.0.md for the schedule and approval details.

8. HUMAN REVIEW / DUPLICATE RESOLUTION

The controlled resolveexception action supports:

Confirm a genuine distinct transaction:
{
  "action": "resolveexception",
  "transactionId": "DEMO-TX-031",
  "resolution": "CONFIRM_DISTINCT",
  "reason": "Verified against the original bank notification",
  "actor": "user"
}

Confirm a duplicate:
{
  "action": "resolveexception",
  "transactionId": "DEMO-TX-032",
  "resolution": "CONFIRM_DUPLICATE",
  "duplicateOf": "DEMO-TX-031",
  "reason": "Both source records describe the same payment",
  "actor": "user"
}

A reason of at least eight characters is required. CONFIRM_DUPLICATE must be an explicit human decision and identify the surviving canonical transaction. Never resolve on similar amount alone.

9. READ / HEALTH ACTIONS

POST JSON actions include:
- health / ping
- validate / validateschema
- gettransaction / gettransactiondetail
- getpendingreview
- getneedsenrichment
- searchtransactions
- getfinancialoverview
- getcategorybreakdown
- getmerchantanalysis
- getrecurringcommitments
- getcashflow
- getspendingbehavior
- getanomalies
- getdataquality

Use getneedsenrichment for category classification gaps. Use getpendingreview for review flags and Source Log conflicts. getdataquality metrics are nested under response.data. Missing Purpose is not part of the required queue.

10. NETWORK RETRIES

If the HTTP action times out:
- Do not alter txnString or originalText for a retry.
- Do not assume the first request failed or succeeded.
- Re-submit the exact same source payload if needed; source hashing/idempotency is designed to recognise exact replays.
- If transactionId is known, query gettransaction.
- Retain requestId and error details for investigation.
- Never create a second payload with shifted fields just to force success.

11. USER-FACING RECEIPT

Keep the normal receipt concise:
- transaction date/time and precision
- merchant
- signed amount
- category
- account/card friendly label
- source verification status
- Transaction ID

Use a distinct warning for REVIEW and SHOW_ERROR. Do not expose raw secrets or unnecessary original source text in a push notification.

12. DEPLOYMENT NOTE

After editing Apps Script source, deploy a new Web App version. The existing /exec deployment does not automatically use unsaved or newly edited source. Validate in staging and run the preflight suite before production deployment.
